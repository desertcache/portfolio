01 Featured program

I built an AI copilot, then took an outsourced support team live on it.

Support agents diagnose point-of-sale integration cases across half a dozen internal systems, graded against a long troubleshooting playbook. The copilot answers from that same playbook, other teams now run their own AI agents inside the workspace, and an outsourced team works live cases in it. This is the whole loop in one program: build it, prove it, roll it out, measure it.

  1. Problem

    Every case meant hopping across a stack of internal tools, and the answer to “what next?” lived in a long playbook agents are audited against. A generic chatbot can't answer from that.

  2. Bet

    Answer from the playbook, not the model. Retrieval runs on the server and returns the sections it used, so every grounded answer cites a real source and the model never gets to invent one.

  3. Build

    A React and TypeScript workspace, a Node backend-for-frontend, and retrieval tuned on the real playbook instead of a test fixture, which exposed four defects the fixture had hidden. Model changes are proven through the company's AI gateway before they ship: a control, the new setting, and a request that should fail. Other teams' agents plug in as panels instead of shipping another tab.

  4. Rollout

    The first outsourced support team couldn't get in, and every failure looked like the same generic error. I proved their access one layer at a time (identity, device trust, app permissions, then a blocked internal call), generated their training kit from one source with a verifier, and now coach their live cases against a resolution-time target.

Partner API Migration

A POS partner sunset its API. I sized the loss, wrote the funding case, and ran the program that kept nearly all of the revenue, under budget.

Timeline

Context

A major POS partner deprecated its v1 API with a large base of active stores still on it, and significant monthly merchant revenue exposed if they didn't move in time. Organic outreach was moving a small fraction of them each week, nowhere near the deadline.

What I built

I co-authored the funding request: sized the risk, modeled four investment options, and recommended white-glove vendor support for the highest-revenue stores. Then I designed the operating model end to end (CRM-routed queues, a fixed follow-up cadence, daily outreach targets, training and escalation paths) and built the dashboard that ran the program, with the full funnel and the revenue at every stage in one view.

The hard part

Deciding where not to spend. White-glove help for every store would have cost far more for little extra revenue, so the plan put the vendor pod on the highest-revenue stores and left the long tail to lighter-touch outreach. Then the pod had to handle a tricky migration without flooding the team with escalations, so I built its training (guides, screenshots, videos, an FAQ) and coached its lead.

Outcome

Nearly all of the at-risk revenue kept, delivered under budget. Escalations fell from daily to a few a week, and the training behind the migration earned a Merchant Services Excellence Award.

AI Enablement, Run Like a Product

Context

Most AI training produces a good afternoon and no change in how work gets done. I co-designed and co-facilitated the first workshop, for senior leaders at the org's leadership summit, then built an org-wide series for an operations organization.

What I built

A four-phase framework leaders reuse, with a hands-on lab where each leader shipped a working AI solution in the room. Then a series where every session ships something people keep using: a skill, a template, a shared team setup. Session four was a builder showcase: people from the business demoed production work they had shipped, and I checked each merge record before describing their work to their executives.

The hard part

Access and hands-on work in the same session deliver neither. A domain owner showed me that midway through, so one planned session became four parts, starting with access and five words: repository, branch, commit, pull request, merge. The line that unlocks a non-technical room is reversibility: everything can be undone, and you're not an admin. When the first attendee hit a wall in the access flow, the path was corrected with screenshots that afternoon, and every access request was granted by the next morning.

Outcome

800+ people trained, a Merchant Services Excellence Award for the leadership workshop, follow-on AI projects in several of the teams that attended, and a series built to count who gets through each step.

Context

Support ran many queues across multiple outsourced vendors on a legacy SaaS tool, and the numbers that mattered were spread across systems that didn't agree with each other.

What I built

A production workforce platform that pulls those sources into one operating surface: dashboard pages covering queue health, SLA, and Erlang C staffing on live Snowflake data. Micro-frontend architecture, plus a typed component library published to the internal registry.

The hard part

Numbers people trust. The upstream systems didn't agree on names, so exact matches were rare; fuzzy matching closed nearly all of the gap. Later, a “fresher” copy of a source table turned out to drop the column one metric depended on, and a drop-in swap would have silently pushed that metric to 100%. A column-by-column parity check caught it, and it now runs before any table swap.

Outcome

An operations lead outside the team independently validated the numbers against the legacy system. The platform has shipped on a weekly release cadence through 2026.

Context

I built a production AI agent for merchant support specialists, and it had an adoption problem. The feedback from the floor: “wall of text, then abandon.”

What I built

Rebuilt the prompt architecture around an enforced six-section answer: What This Means, Diagnostic Checklist, Action Matrix, Outreach Script, Still Stuck?, and CRM Reminder. Prose became something an agent can scan and act on.

The hard part

Format is the feature. Agents read under time pressure, so every answer leads with what to do next and keeps the same six sections, every time.

Answers shrank to a fraction of their old length while holding accuracy. It led adoption among the internal AI agents, and other agents now reuse the template.

The org's first cost-per-task model on live warehouse data: cost per touch and per completed task, in-house and vendor, with a lineage tab that shows the exact query and a worked example. 03 How I build

I build in Claude Code every day, and I run it like a team.

I give it what I'd give any team: a playbook, shared memory, the right tools, and a review before anything ships. Most of it is public, so you can check the work.

  1. Fleet

    Big builds run as a fleet of Claude agents in Claude Code. On Starship Explorer, an orchestrator wrote the design contracts, Sonnet and Opus agents built in parallel lanes on separate files, and nothing merged until a reviewer signed off on types, functional tests, real-GPU screenshots and a frame-time budget. The contracts and gates are in the repo.

  2. Skills

    Work I repeat becomes a skill: a written procedure with its own checks, so every run goes the same way. Mine brief a session, run a retro, red-team a plan, and publish this site's Hill Money Watch digest through a script that rejects any draft that breaks the contract.

  3. Hooks

    Hooks do what shouldn't depend on anyone remembering: each session opens with the project's state already loaded, and every commit is logged for the retro.

  4. Memory

    Decisions, error patterns and fixes carry over between sessions, and a mistake that shows up three times becomes a written rule. I open-sourced the core of it as agent-os: hooks, skills, memory and a session lifecycle for Claude Code.

  5. MCP

    MCP servers give agents real tools instead of guesses: a browser to test in, current library docs, the data a task needs. When nothing fits, I build the server.

  6. Evals

    Model changes pass a test before they ship. On the copilot, a retrieval change had to rescue questions that used to come back empty without pushing a right answer down. The answer bar on this page is scored on questions written before any model saw them: right first 81% of the time, in the top three 93%, and a test fails if an edit lowers either. How I work

  • 01Measure on the real thing. A test fixture hid four retrieval bugs; the real playbook exposed them.
  • 02Two agreeing documents are one source. Load the live page before trusting either.
  • 03“The code exists” isn't “the user can do it.” Before promising what an AI can resolve, list the actions it can actually reach.
  • 04Count adoption, not attendance. Every session ends with something people keep using, and I track who gets through each step.
  • 05A fix is done when every copy is fixed. Fetch it back from wherever people actually read it, then check it.
